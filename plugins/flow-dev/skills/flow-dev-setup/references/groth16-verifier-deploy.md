# Deploying snarkjs Groth16 Verifiers on Flow EVM

Flow EVM is fully compatible with the Ethereum zk-SNARK tooling stack — snarkjs, circom, Hardhat, ethers.js. Verifier contracts generated by `snarkjs zkey export solidityverifier` deploy and run unmodified on Flow EVM. The BN254 precompiles (`0x06` ECADD, `0x07` ECMUL, `0x08` ECPAIRING) sit at the same addresses with the same input/output ABI as Ethereum mainnet, because Flow EVM tracks the Ethereum reference implementation (go-ethereum) byte-for-byte.

There is one detail that bites every team the first time they wire snarkjs proofs into an on-chain verifier — and it is **not** Flow-specific.

## The Fp2 Ordering Convention

EIP-197 (the ECPAIRING precompile spec) requires that each Fp2 element of a G2 point be encoded as `(imaginary, real)` — the imaginary coefficient first, real coefficient second. This is the convention used by `bn256.G2.Marshal` in go-ethereum and by every conforming EVM implementation.

`snarkjs` emits `proof.json` with G2 elements (specifically `pi_b`) ordered the opposite way: `(real, imaginary)`. If you pass `pi_b` straight from `proof.json` into the verifier's calldata, the pairing precompile reads the field elements with the coefficients swapped, the pairing check fails, and `verifyProof()` returns `false` — even though the proof is mathematically valid.

The off-chain `snarkjs.groth16.verify()` function does not exhibit this mismatch because it normalizes the ordering internally before checking. The discrepancy only surfaces when the proof is encoded for an on-chain call.

**This is not a Flow EVM workaround.** It is EIP-197 behavior. Every EVM chain — Ethereum L1, Polygon, Arbitrum, Optimism, Flow EVM — requires the same swap when consuming a snarkjs-generated proof.

## Empirical Confirmation

Identical proof.json + public.json + Verifier.sol (solc 0.7.6, snarkjs Groth16 template):

| Environment | chainId | `pi_b` natural | `pi_b` swapped |
|---|---|---|---|
| Hardhat localhost (go-ethereum reference) | 31337 | `false` | `true` |
| Flow EVM emulator + gateway (`--evm-network-id=preview`) | 646 | `false` | `true` |

Hardhat localhost uses the geth-canonical BN254 precompile. Flow EVM matches it. The two environments produce identical pairing-check outputs for both proof encodings.

## The Swap (Reference Implementation)

Apply the swap only to `pi_b`. `pi_a` and `pi_c` are G1 points with single Fp elements — no Fp2 ordering exists for them.

```typescript
type SnarkjsProof = {
  pi_a: [string, string, string];
  pi_b: [[string, string], [string, string], [string, string]];
  pi_c: [string, string, string];
};

function formatProofForVerifier(proof: SnarkjsProof) {
  return {
    a: [proof.pi_a[0], proof.pi_a[1]] as const,
    b: [
      [proof.pi_b[0][1], proof.pi_b[0][0]],   // Fp2: swap (re, im) -> (im, re)
      [proof.pi_b[1][1], proof.pi_b[1][0]],
    ] as const,
    c: [proof.pi_c[0], proof.pi_c[1]] as const,
  };
}
```

Then encode `(a, b, c, publicSignals)` per the verifier's ABI:

```typescript
const formatted = formatProofForVerifier(proof);
const ok = await verifier.verifyProof(
  formatted.a,
  formatted.b,
  formatted.c,
  publicSignals,
);
```

The `[2]`-element-only of `pi_a` / `pi_b` / `pi_c` (the third coordinate is `"1"`, the projective z-coordinate) is intentional — the on-chain verifier expects affine coordinates.

## Flow EVM chainIds (for hardhat.config.ts)

When deploying via Hardhat, set `chainId` explicitly per target. Auto-detection works for read-only calls but signed transactions encode the chainId in their EIP-155 signature; a mismatch between the network's actual chainId and the one your wallet signs against will be rejected.

| Target | chainId | RPC |
|---|---|---|
| Local emulator + gateway with `--evm-network-id=preview` | 646 | `http://127.0.0.1:8888` (or whatever `--rpc-port` you set) |
| Local emulator + gateway default (`--evm-network-id=testnet`) | 545 | same |
| Flow EVM Testnet | 545 | `https://testnet.evm.nodes.onflow.org` |
| Flow EVM Mainnet | 747 | `https://mainnet.evm.nodes.onflow.org` |

Two things to keep aligned: the gateway's `--evm-network-id` flag and Hardhat's `chainId`. They must match, or signed transactions will fail with a chain-ID mismatch even though `eth_chainId` reads cleanly.

```typescript
// hardhat.config.ts — local development with the gateway on preview
flowLocal: {
  url: 'http://127.0.0.1:8888',
  chainId: 646,                            // must match --evm-network-id=preview
  accounts: [process.env.DEPLOYER_KEY!],
},
```

## Workflow Checklist

1. Generate the verifier: `snarkjs zkey export solidityverifier circuit.zkey Verifier.sol`
2. Compile and deploy with Hardhat (Solidity 0.7.6 or newer; the snarkjs template targets 0.7.6 by default).
3. Before each on-chain call, **transform the proof through `formatProofForVerifier`** — do not pass `proof.pi_b` directly.
4. **Always run an on-chain verification test against a freshly-generated proof.** `snarkjs.verify()` succeeding off-chain is not a substitute. The Fp2 mismatch is invisible until the precompile is invoked.
5. When switching targets (local emulator → testnet → mainnet), update Hardhat's `chainId` to match the target's actual value.

## Common Failure Modes

- **`verifyProof()` returns `false` for a proof that `snarkjs.verify()` accepts** — you forgot the `pi_b` swap. Apply `formatProofForVerifier` and retry.
- **Gas exhaustion during pairing** — `0x08` ECPAIRING costs `45,000·k + 34,000` gas where `k` is the number of pairs. A Groth16 verification is `k=4`, costing ~214,000 gas baseline. Make sure `gasLimit` on the verifier call exceeds 300,000 to leave headroom for surrounding logic.
- **Mismatched `publicSignals` length** — the snarkjs verifier expects the public-input array to match the circuit's declared public count exactly. An off-by-one in the array length will revert before pairing runs.
- **Signed-tx rejection with "invalid chain id"** — gateway's `--evm-network-id` and Hardhat's `chainId` are out of sync. Realign them.
